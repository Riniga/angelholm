## Project Overview

This workspace contains an urban mobility simulation project for modelling how people move through a real city using cars, bicycles, walking and potentially other transport modes.

The project is intended to provide an experimental environment where infrastructure and traffic conditions can be changed and the resulting effects on mobility can be simulated, measured and compared. See [`docs/vision.md`](../vision.md) for the full purpose and principles, and [`docs/roadmap.md`](../roadmap.md) for the planned delivery stages (R0–R5).

**No application code exists yet.** There is no `apps/`, no `packages/`, and no automated tests. The repository was initialised from a generic, organisation-wide reference skeleton (referred to in the repository as a "grundplåt") that ships a working development process, quality gates and AI-collaboration structure before any project-specific code is written; its bootstrap instructions (`_LÄS-MIG-FÖRST.md`) have all been carried out and the file deleted, per its own instruction. Project-identity placeholders (project name, Conda environment name, security contact) have been replaced across `README.md`, `AGENTS.md`, `SECURITY.md`, `environment.yml`, `docs/development/setup.md`/`environment.md`, `.github/workflows/ci.yml`, `docs/vision.md`, `docs/roadmap.md`, and this file, and a real, verified `requirements-lock.txt` exists. Two real MVPs with implementation plans are written and ready — `docs/mvp/000-workspace-foundation.md` (ADRs, methodology-compliance baseline, repo settings) and `docs/mvp/001-first-traffic-simulator.md` (the first actual application) — but neither has been implemented yet. The placeholders that remain all depend on an app or package that doesn't exist yet (`pyproject.toml`, `pytest.ini`, `.env.example`, parts of `ci.yml`) — see "Open Questions and Areas Not Yet Implemented" below.

## Major Components

No application components have yet been implemented.

The following architectural responsibilities have been identified from `docs/vision.md` but should not be considered implemented components.

### Geographic Model

Responsible for representing the physical city and its transport network.

Expected information includes:

* Roads and intersections.
* Lanes and permitted transport modes.
* Pedestrian and bicycle infrastructure.
* Speed limits and other network restrictions.
* Geographic features needed for visualization.

OpenStreetMap is currently the primary candidate source for geographic data.

### Mobility Simulation

Responsible for executing movements through the transport network.

The current primary candidate is **SUMO (Simulation of Urban MObility)**.

Expected responsibilities include:

* Vehicle movement.
* Pedestrian and bicycle movement.
* Routing.
* Traffic interactions.
* Traffic signals.
* Congestion.
* Dynamic changes to the transport network.

### Population and Travel Demand

Responsible for defining why traffic exists.

The intended model is person-oriented rather than vehicle-oriented. A person may have:

* Origin.
* Destination.
* Departure time.
* Available transport modes.
* Vehicle ownership.
* Daily activities and journeys.

This component does not yet exist.

### Scenario and Experiment Layer

Responsible for defining controlled changes to the simulated city.

Examples include:

* Closing a road.
* Opening a new connection.
* Changing road capacity.
* Restricting transport modes.
* Modifying traffic rules.

The same population and travel demand should be reusable across scenarios to make comparisons meaningful.

### Analysis

Responsible for collecting and comparing simulation results.

Potential measurements include:

* Travel time.
* Delay.
* Congestion.
* Queue lengths.
* Traffic volumes.
* Route changes.
* Effects on individual journeys.

### Visualization and User Interface

A dedicated user interface has not yet been selected or implemented.

SUMO's existing visualization capabilities are expected to be sufficient during the initial MVPs.

A dedicated interactive map and experiment interface may be introduced later if required.

## Architectural Observations

### The repository started as a generic skeleton, now bootstrapped

The repository was initialised from a generic, organisation-wide reference skeleton (the
"grundplåt"; its bootstrap instructions lived in `_LÄS-MIG-FÖRST.md`, deleted once every
step it described was carried out). Project-identity values (project name, Conda
environment name, security contact) were resolved across `README.md`, `AGENTS.md`,
`SECURITY.md`, `environment.yml`, `docs/development/setup.md`/`environment.md`,
`.github/workflows/ci.yml`, and `docs/architecture/current-state.md`; a real,
verified-not-drifted `requirements-lock.txt` now exists. What remains templated is exactly
the set of placeholders that depend on an app or package actually existing (`pyproject.toml`,
`pytest.ini`, `.env.example`, parts of `ci.yml` — see `docs/plans/001-first-traffic-simulator.plan.md`
Phase 2, which resolves them) plus the methodology-compliance records
(`docs/methodology-compliance/*`, still structure-only — tracked by
`docs/mvp/000-workspace-foundation.md`). Treat any tooling/process claim from those
still-templated files as aspirational until their placeholders are resolved.

### Separate the City from the Traffic

The geographic model describes what infrastructure exists.

Travel demand describes who wants to travel, where and when.

The simulation engine determines what happens when those journeys interact with the infrastructure.

Keeping these concerns separate is important for reproducible experiments.

### People Generate Traffic

The long-term domain model should treat people and their mobility needs as the origin of traffic.

Vehicles are resources used by people rather than the fundamental unit of the system.

Early MVPs may generate vehicles directly as a simplification.

### Scenarios Should Be Reproducible

Experiments should be based on a known baseline.

For example:

```text
City
   +
Population
   +
Travel Demand
   ↓
Baseline Simulation
```

A scenario changes one or more controlled conditions:

```text
Same City
   +
Same Population
   +
Same Travel Demand
   +
Road Closure
   ↓
Scenario Simulation
```

The difference between the results is then measurable.

### Simulation Engine Should Remain Replaceable

Domain concepts such as people, journeys, scenarios and experiment results should not unnecessarily depend on SUMO-specific representations.

SUMO is currently the strongest candidate simulation engine, but the project's own domain model should remain conceptually separate from it.

### Prefer Existing Capabilities

The project should not implement its own traffic simulation, routing or geographic database where established tools already provide suitable capabilities.

Project-specific development should primarily focus on:

* Travel demand.
* Population modelling.
* Scenario management.
* Experiment orchestration.
* Analysis.
* User interaction.
