# MVP-002 Plan – Extended Map Area

Implements [`docs/mvp/002-extended-map-area.md`](../mvp/002-extended-map-area.md).

**Status:** Complete — all 4 phases done, MVP closed 2026-09-18 as delivered. See the
MVP's "Outcome at close" for verification detail.

## 1. Goal

Replace MVP-001's small neighbourhood network with a routable SUMO network covering the
area outlined in `docs/architecture/mapoutline.png`, clipped to the drawn outline (not its
bounding box), while keeping the rest of the pipeline (`fetch → build → generate traffic →
write config → run`) unchanged. Map context features (water, land use) stay out of scope —
see MVP-003.

Every step below is executable directly (terminal commands, file edits, script runs) —
there is no step that depends on a human doing manual GIS tracing in an external tool. The
one genuinely manual step — the project owner confirming the rendered result matches their
intent — is the closing acceptance check, not an implementation TODO.

## 2. Assumptions

* **Confirmed in this environment**: `netconvert --help` (installed `eclipse-sumo==1.27.1`,
  matching `apps/simulator/pyproject.toml`'s pin) exposes
  `--keep-edges.in-geo-boundary STR[]` — "Only keep edges which are located within the
  given boundary (given either as GEODETIC corner coordinates
  `<lon-min,lat-min,lon-max,lat-max>` or as polygon `<lon0,lat0,lon1,lat1,...>`)". This is
  exactly the outline-polygon clip this MVP needs, works directly in WGS84 lon/lat (no
  manual projection step required), and is already installed — no dependency risk here.
* The two corners the project owner gave describe the **image's own corners**, not just the
  outline's bounding box: `mapoutline.png` pixel `(0, 0)` = 56.255099, 12.849519 (NW) and
  pixel `(width, height)` = 56.225986, 12.894902 (SE). This lets pixel coordinates traced
  from the image be converted to lon/lat by plain linear interpolation — accurate enough at
  this scale (~3.2 km × 2.9 km; equirectangular distortion over that extent is negligible
  for a visualization-scale polygon, not a survey-grade one).
* The red outline drawn in the image is a distinct, identifiable color from the basemap's
  own colors (roads, water, the route-`107` shield). This must be confirmed by sampling
  actual pixel values from the image during Phase 1 (TODO 2 below) — not guessed in this
  plan — because the basemap itself uses red/orange tones for major roads.
* `osmGet.py`'s `-b` bbox argument order is `west,south,east,north`, matching the existing
  `DEFAULT_BBOX` convention in `network.py`.
* New dependencies are needed and are justified below (§3); per
  [`docs/standards/dependencies.md`](../standards/dependencies.md) they go in
  `requirements.in` (+ `apps/simulator/pyproject.toml` for the one that becomes an actual
  runtime import of the `simulator` package), locked via `pip-compile`, and get an ADR for
  the one that's a real production dependency (`shapely`).
* The existing test suite's pattern (mock `subprocess.run`, no live network/SUMO calls,
  `tmp_path` fixtures) is reused as-is for `network.py` changes.
* `pytest` coverage floor (95%, `ADR-004`) must still hold after this change. The
  one-off digitization script is not part of `apps/simulator/src` and is not covered by
  that floor (mirrors `scripts/scan_instruction_files.py`'s standing today — repo-root
  tooling, not app code).

## 4. Step-by-step TODO, grouped into phases

### Phase 1 — Extract the coverage outline as GeoJSON

*(commit message: "Extract MVP-002 coverage outline from mapoutline.png as GeoJSON")*

1. Add `numpy`, `opencv-python-headless`, `shapely` to `requirements.in` with a short
   comment explaining each's purpose (mirroring the existing comment style in that file).
   Recompile: `pip-compile --generate-hashes --no-annotate --no-header --output-file=requirements-lock.txt requirements.in`.
   Add `shapely` to `apps/simulator/pyproject.toml`'s `dependencies`.
2. Write a tiny throwaway probe (or a `--probe` mode in the script itself) that loads
   `docs/architecture/mapoutline.png` with `cv2.imread`, samples pixel colors along a few
   points visibly on the drawn red outline, and prints their BGR values — to pin down the
   exact color (and how far it is from the basemap's own red/orange road tones) before
   writing the real thresholding logic.
3. Write `scripts/extract_coverage_outline.py`:
   * Load the image; build a boolean mask for pixels within a small tolerance of the
     outline color found in TODO 2.
   * `cv2.morphologyEx(..., cv2.MORPH_CLOSE, ...)` to bridge any small anti-aliasing gaps
     in the hand-drawn line.
   * `cv2.findContours(mask, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)`; pick the
     largest-area contour (the outline loop itself, not stray noise pixels).
   * `cv2.approxPolyDP` to simplify the contour to a reasonable vertex count (tune epsilon
     as a small fraction, e.g. 0.2–0.5%, of the contour's perimeter).
   * Convert each `(px, py)` vertex to `(lon, lat)` via linear interpolation against the
     image's pixel dimensions and the two known corner coordinates (per §2's assumption).
   * Build a `shapely.Polygon` from the result; validate it (`.is_valid`), and compute its
     bounding box for a sanity check against the project owner's two given corners (should
     be close, not necessarily exact, since the drawn shape isn't a rectangle).
   * Write `docs/architecture/coverage-outline.geojson` (single `Polygon` feature, `[lon,
     lat]` order).
   * Render a debug overlay: redraw the extracted polygon on top of the original image and
     save as `docs/architecture/coverage-outline-check.png`.
4. Run the script: `python scripts/extract_coverage_outline.py`.
5. Open `coverage-outline-check.png` and confirm by inspection that the extracted polygon
   traces the same shape as the hand-drawn red line in `mapoutline.png` — if it doesn't
   (wrong color tolerance, morphology too aggressive, wrong contour picked), adjust the
   script and re-run before moving on.
6. Copy the resulting `docs/architecture/coverage-outline.geojson` to
   `apps/simulator/data/coverage-outline.geojson`.

## 5. Risks / open questions

* **Outline-color separation from the basemap.** The main real risk left in this plan:
  if the hand-drawn outline's color is too close to the basemap's own red/orange road
  tones, naive color thresholding in Phase 1 will pick up stray road segments as "outline".
  Mitigated by the explicit color-probe step (TODO 2) and the mandatory visual check
  against `coverage-outline-check.png` (TODO 5) before the polygon is ever used for a real
  `netconvert` run — a bad extraction is caught by inspection, not silently baked in.
* **Network size growth.** The area is roughly 5–6× larger by bounding box than MVP-001's
  extract; artifact file sizes and `netconvert`/`randomTrips.py` runtimes will grow —
  budget time in Phase 3 rather than assuming a drop-in re-run.
* **Traffic volume at the new scale.** MVP-001's `MIN_VEHICLES=10` / default `period=15s`
  was tuned for a small extract; at the new scale the same settings may look visually
  sparse. Left as a Phase 3 tuning choice, not a hard acceptance criterion — deliberately
  not scope-creeping this MVP into demand modelling (that belongs to R2).
* **No map-context features yet.** Until MVP-003 lands, the larger area's GUI will still be
  a bare grey road network with no water/landmarks to visually orient against — worth
  setting that expectation with the project owner ahead of the Phase 4 visual check.
